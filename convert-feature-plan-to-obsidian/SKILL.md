# Convert Plan-Feature HTML to Obsidian Markdown

Import `/plan-feature` HTML documents into Obsidian as clean, readable Markdown. Preserve the substance and the established note style rather than the web page's CSS, navigation, or controls.

## Style to Match

- Use the HTML `<h1>` text as the note title and filename, not as a top-level `#` inside the note.
- Name files `NN - Title.md`, where `NN` is the leading number from the HTML filename (for example, `00-pipeline.html` becomes `00 - Gaming Texture Pipeline.md`).
- Start each note with `*Feature Plan*`, a blank line, and the short description from `.hero-sub`.
- Preserve meaningful sections and their hierarchy. The first section should remain `## 0. Requirements Analysis`; retain the A/B/C and closing headings, subsections, and step numbers.
- Convert the chosen-solution comparison into Obsidian callouts: `[!success] Pro: Chosen Solution`, `[!failure] Contra: Chosen Solution`, and `[!info] RECOMMENDATION`. Preserve their complete text.
- Render diagrams as fenced `mermaid` blocks, source code as fenced blocks with a language when identifiable, and HTML tables as Markdown pipe tables. Retain links, bold/italic emphasis, lists, quotes, assumptions, open questions, and technical detail.
- Do not add YAML frontmatter, a duplicate H1, CSS, scripts, buttons, or the rendered Mermaid preview.
- Use UTF-8 and sensible blank lines. Ensure a space separates a numbered implementation step from its title.

## Workflow

1. Identify the project root and the intended Obsidian vault. The default HTML source is `<project root>\doc\plans`; import all HTML documents there. Honor a different source directory or explicit file list if the user specifies one. Prefer an available Obsidian integration for vault resolution. Otherwise, resolve the vault from Obsidian's local vault registry or ask the user if more than one vault could be intended; never guess a vault from its folder name.
2. If `doc\plans` does not exist and the user did not specify another source, do not silently fall back to `plans`, another folder, or the whole workspace. Look for candidate HTML files in the project, report their paths, and ask the user which files should be transferred using `ask_user`. Only convert the files the user selects, passing them explicitly with `-HtmlFiles`. If no candidate files are found, ask the user for the source folder or HTML file paths.
3. Use this vault layout: `<vault>\Projekte\<project>\Planing`. Identify the project folder from the project root directory name, not from the `doc` or `plans` source folder. Find `Projekte` in the vault without regard to case and select the matching project subfolder without regard to case. If no matching project folder exists, create it inside `Projekte` using the project name. Inside the selected project folder, reuse its existing `Planing` subfolder (case-insensitive); if it is absent, create exactly `Planing`. Do not write notes directly into `Projekte`, into the vault root, or into another project's folder.
4. Inspect the selected `Planing` folder before converting. Treat manually edited notes there as the style authority; retain their naming, title, heading, callout, and table conventions.
5. Run the bundled [HTML-to-Markdown converter](./scripts/convert-plan-html.ps1) with `-ProjectDirectory`, `-VaultPath`, and `-ProjectName` for the default source. It reads all `*.html` files under `<project root>\doc\plans` recursively. For a user-selected set of files use `-HtmlFiles` with those exact paths and the same project/vault arguments. For a user-specified alternate source directory, use `-SourceDirectory` together with the project/vault arguments. The converter creates missing project/`Planing` folders under `Projekte` and supports `-WhatIf` to preview creation. It skips notes that already exist; use `-Overwrite` only after the user explicitly asks to replace them.
6. Review the generated notes against both the HTML and neighboring curated notes. Verify titles and filenames, complete section coverage, intact code and Mermaid fences, valid pipe tables, preserved callout text, UTF-8 characters, and that no HTML layout or control markup leaked through.
7. Report the created and skipped notes with links to the resulting vault files. Do not delete, rename, or replace existing notes as part of a normal import.

## Converter

PowerShell 5.1 or later is sufficient; no external packages are required. Example:

```powershell
& "$HOME\.copilot\skills\plan-feature-to-obsidian\scripts\convert-plan-html.ps1" `
  -ProjectDirectory "C:\path\to\project" `
  -VaultPath "C:\path\to\vault" `
  -ProjectName "project"
```

By default this imports every HTML document under `C:\path\to\project\doc\plans` into `C:\path\to\vault\Projekte\project\Planing`, reusing matching folder names case-insensitively. If the default source folder is missing, the script stops with an explicit error; ask the user which project HTML files to import and pass those exact paths with `-HtmlFiles`, or use an alternate `-SourceDirectory` the user provides. `-ProjectName` is optional when `-ProjectDirectory` is set. To deliberately regenerate existing notes, add `-Overwrite` only with the user's approval. Preview folder and note creation with `-WhatIf`.
